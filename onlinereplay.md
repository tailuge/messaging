# Nchan Message Replay & Lobby Presence Documentation

This document explains how the Billiards Lobby processes presence messages to determine user online status, specifically focusing on how Nchan's message replay affects the UI state.

## Nchan Configuration

The Nchan server is configured as the messaging backbone. For the presence channel (`presence/lobby`), the following settings in `docker/nchan.conf` are critical:

- **Buffer Length**: `nchan_message_buffer_length 2000;` - Up to 2000 recent messages are kept in memory.
- **Message Timeout**: `nchan_message_timeout 90s;` - Messages older than 90 seconds are evicted from the buffer.
- **Replay Strategy**: `nchan_subscriber_first_message oldest;` - When a client connects, Nchan immediately replays all non-expired messages in the buffer in chronological order.

## Lobby Presence Processing Logic

The `Lobby` class in `src/lobby.ts` manages the `users` Map. It processes incoming messages via `handlePresenceUpdate`.

### Message Types
1. **`join`**: Published by the client when the lobby is first opened.
2. **`heartbeat`**: Published by the client every 60 seconds (by default) to maintain presence.
3. **`leave`**:
   - **Explicit**: Published by the client when the user clicks "Leave" or the tab is closed (via `keepalive` fetch).
   - **Automatic**: Published by the Nginx server via the `presence_unsub` NJS hook when a WebSocket connection is closed.

### The `handlePresenceUpdate` Algorithm

```typescript
private handlePresenceUpdate(msg: PresenceMessage): void {
  const existing = this.users.get(msg.userId);

  if (msg.type === "leave") {
    if (existing) {
      this.users.delete(msg.userId);
      this.cachedUsersList = null;
      this.notifyListeners();
    }
  } else if (msg.type === "join") {
    this.users.set(msg.userId, msg);
    this.cachedUsersList = null;
    this.notifyListeners();
  } else {
    // Heartbeat or other update
    const changed = !existing || this.hasMeaningfulChange(existing, msg);
    this.users.set(msg.userId, msg);
    if (changed) {
      this.cachedUsersList = null;
      this.notifyListeners();
    }
  }
}
```

## The "Missing User" Problem: Online -> Offline -> Online

The system occasionally fails to show a user as online even if they have just reconnected. This is caused by a race condition between client-side `join` messages and server-side `leave` (unsub) messages during the Nchan replay.

### The Scenario: Page Refresh
1. **Session A**: User is online. Nchan buffer contains Session A heartbeats.
2. **Refresh**: User refreshes the page.
3. **Unsubscribe**: Session A's WebSocket closes. Nginx/Nchan triggers `presence_unsub` which publishes a `leave` message for `userId`.
4. **Session B**: User's new page loads and publishes a `join` message.
5. **Nchan Replay**: The Nchan buffer now contains (roughly in order):
   - `[Session A Heartbeat]`
   - `[Session B Join]`
   - `[Session A Leave]` (Auto-published by the server because of the refresh)

### The Failure Mode
Because `handlePresenceUpdate` **does not check timestamps** (`meta.ts`), it processes messages in the order Nchan delivers them.

If the `leave` message from the old session is published (or received by Nchan) *after* the `join` message from the new session, the following happens during replay:
1. `join` (Session B) is processed: User is added to `this.users`.
2. `leave` (Session A) is processed: User is **deleted** from `this.users`.

The user is now online but invisible in the lobby. They will only reappear when their next `heartbeat` (Session B) is published (up to 60 seconds later).

## Key Deficiencies

### 1. Lack of Timestamp Ordering
The code currently assumes: *"Nchan guarantees ordered delivery, so we don't need to check meta.ts for ordering."*
While true for a single connection's stream, it is **not true for the logical state of a user**. A `leave` message generated by a server-side timeout or connection close can logically "belong" to an older session than a `join` message from a newer one, even if Nchan sequences them in a way that puts the `leave` last.

### 2. Missing `nchan_subscriber_id`
In `docker/nchan.conf`, the subscriber is identified by `$arg_uid`, but Nchan is not configured to treat multiple connections with the same UID as a single logical subscriber. This means:
- If a user has 3 tabs open, closing *any* tab triggers a `presence_unsub` and a global `leave` message.
- The other 2 tabs see the `leave` and remove the user from their UI, even though the user still has 2 tabs active.

## Summary of Fixes Required
- **Timestamp Validation**: `handlePresenceUpdate` must compare `msg.meta.ts` with the `ts` of the `existing` user record. If the incoming message is older than what we already know, it should be ignored.
- **Subscriber Unification**: Use `nchan_subscriber_id $arg_uid;` in the Nginx configuration to ensure `presence_sub` and `presence_unsub` only trigger for the *first* connect and *last* disconnect of a specific user ID.
