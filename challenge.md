# Challenge Flow Specification

This document outlines the sequence of messages and network paths involved in the peer-to-peer challenge flow within the messaging library.

## Nchan Paths

Challenges are broadcast over the same channels used for lobby presence to simplify subscription management.

- **Publish Path**: `/publish/status/lobby`
- **Subscribe Path**: `/subscribe/status/lobby`

## Message Lifecycle

The challenge flow follows a standard request-response pattern using four main message types: `offer`, `accept`, `decline`, and `cancel`.

### 1. Challenge Offer (`offer`)
Sent by the **Challenger** to initiate a game.

```json
{
  "messageType": "challenge",
  "type": "offer",
  "challengerId": "alice-123",
  "challengerName": "Alice",
  "recipientId": "bob-456",
  "ruleType": "8-ball",
  "tableId": "random-table-id"
}
```

- **tableId**: Generated by the library using `getUID()` before sending the offer.

### 2. Challenge Acceptance (`accept`)
Sent by the **Recipient** to confirm they want to play.

```json
{
  "messageType": "challenge",
  "type": "accept",
  "challengerId": "bob-456",
  "challengerName": "Bob",
  "recipientId": "alice-123",
  "ruleType": "8-ball",
  "tableId": "random-table-id"
}
```

- Both players then join the `Table` identified by `tableId`.

### 3. Challenge Decline (`decline`)
Sent by the **Recipient** to reject the offer.

```json
{
  "messageType": "challenge",
  "type": "decline",
  "challengerId": "bob-456",
  "challengerName": "Bob",
  "recipientId": "alice-123",
  "ruleType": "8-ball"
}
```

### 4. Challenge Cancellation (`cancel`)
Sent by the **Challenger** to withdraw the offer before it is accepted or declined.

```json
{
  "messageType": "challenge",
  "type": "cancel",
  "challengerId": "alice-123",
  "challengerName": "Alice",
  "recipientId": "bob-456",
  "ruleType": "8-ball"
}
```

## Library Implementation (`Lobby` class)

The `Lobby` class provides high-level methods to manage these messages:

- `challenge(userId, ruleType)`: Generates a UID, publishes an `offer`, and returns the `tableId`.
- `acceptChallenge(userId, ruleType, tableId)`: Publishes an `accept` message and updates presence to show we've joined the table. The table itself is joined via `MessagingClient.joinTable()` with the same `tableId`.
- `declineChallenge(userId, ruleType)`: Publishes a `decline` message.
- `cancelChallenge(userId, ruleType)`: Publishes a `cancel` message.
- `onChallenge(callback)`: Allows the consumer to listen for incoming challenges directed at them.

The library filters incoming messages on the lobby subscription. Only `ChallengeMessage` objects where `recipientId` matches the current user's ID are emitted via `onChallenge`.

## Disconnection and Rejoin Scenarios

A common concern is whether a challenged person can see a challenge sent while they were briefly disconnected or if they refresh the page.

### Message Retention
The Nchan server is configured to retain messages in a buffer:
- `nchan_message_buffer_length 2000`
- `nchan_message_timeout 90s`

### Reconnection Behavior
When a client connects (or reconnects) to the lobby, it uses:
- `nchan_subscriber_first_message oldest`

**Result**: Upon joining the lobby, the Nchan server sends the entire buffer of recent messages (up to 90 seconds old) to the client.

### Can a challenged person see a previous challenge?
**Yes.** If Alice sends a challenge to Bob, and Bob refreshes his page or loses connection for 30 seconds:
1. Bob reconnects and joins the lobby.
2. Nchan replays the buffered messages to Bob.
3. The library parses the `offer` message from Alice.
4. The library triggers Bob's `onChallenge` callback.
5. Bob sees the challenge and can accept it.

**Note**: Since challenges are P2P and rely on buffered replay, it is the responsibility of the UI to handle "stale" challenges (e.g., if Alice has already left the lobby, her presence heartbeat will be missing from the user list).
